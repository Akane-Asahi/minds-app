# 01 Core (always load this first)

MINDS = Metacognitive Interface for Navigating Directions & Scaffolding. An LLM-assisted
academic search interface (University of Regina library search, Ex Libris Primo, branded
"Quick Find") for people with dyslexia and/or low working memory. It is the experimental
condition of a within-subjects lab study; the control is the Baseline app (this repo started
from the Baseline code).

## The problem in five lines

1. People with dyslexia are often unsure what to search for and favour familiar sources and
   angles, so their search narrows to familiar ground.
2. Complex tasks turn into exploratory search that spans several sessions; on return the
   searcher has lost the thread (the scarce resource is working memory, not time).
3. MINDS has an LLM propose **search directions** (about half of them unfamiliar angles) so
   the searcher plans before searching.
4. It scores each result against each direction, so a result shows at a glance why it may
   help, and saving a result files it under a direction.
5. It keeps a low-text, visible record across sessions so a returning searcher can resume
   or choose a new direction. The LLM is a first draft of the searcher's thinking, never an
   authority.

| Say | Means | Do not say |
|---|---|---|

## Rules that must not be broken

1. **Counts are plain counts.** Saved and coverage counts are never a percentage or a ratio
   of the Primo total. The grey bar track is a ruler only: never labelled, never a target.
2. **Derive, never store twice.** Per-direction and per-session numbers come from grouping
   `saved_results` (and `session_results` for "reviewed"). No stored counters.
3. **Clarity (thumbs) is never LLM-inferred.** (Feature deferred; the rule stays.)
4. **Every LLM output is structured JSON** (validated server-side), **editable or
   dismissible in one tap, and has a one-line "why"** reachable by tap (the `?`, the
   rationale on suggested directions).
5. **Batch, do not loop.** One scoring call per pool. Skip result/direction pairs already in
   `result_scores`.
6. **New directions never affect ranking.** Ranking uses the active selected direction only.
7. **Primo metadata only.** Descriptions on cards come from Primo, never generated. No full
   text is fetched. Primo and LLM API keys stay server-side, never in the browser.

## Constants (named constants in code, tune in testing)

| Constant | Value | Meaning |
|---|---|---|
| `DIRECTION_COUNT` | 8 | directions generated by 5.1 (about half `new`) |
| `CANDIDATE_POOL_SIZE` | 10 | Primo results fetched and scored per search (= Baseline page size) |
| `CHIP_COUNT` | 3 | selected-direction chips shown by default per card |
| `SCORE_MIN` / `SCORE_MAX` | 0 / 5 | whole numbers; server floors decimals and clamps |
| `SUGGEST_MIN_COUNT` | 3 | saved results needed before detection runs, and distinct saved results that must support a topic |
| `EMERGING_GOAL_MIN` | 2 | a new direction needs goal relevance **strictly greater** than this |
| `SUGGESTION_LIMIT` | 3 | max active suggested new directions |
| `SESSION_GAP` | 1 hour | idle **more than** this starts a new session |
| `IDLE_CAP` | 5 minutes | idle stretches count as at most this toward `active_seconds` |
| `MAX_SNAPSHOT_BLOCKS` | 6 | journey-strip blocks before "+N more" |
| `BAR_MIN_CAPACITY` | 10 | bar scale: unit = trackWidth / max(BAR_MIN_CAPACITY, largest total) |
| `MIN_SEGMENT_PX` | 32 | minimum bar segment width |
| Primo cache TTL | about 24 h | cache keyed by normalized query |

Removed (do not reintroduce): `MIN_CHIP_SCORE`, `STRONG_MATCH_SCORE`, `EMERGING_MIN_SCORE`,
`SUGGEST_WINDOW`, `EMERGING_START_SAVES`.

## Architecture (MERN, see /stack_changed.md for what differs from Baseline)

```
React 18 + MUI v5 (frontend)  ->  Express API (orchestration)  ->  MongoDB (Mongoose)
                                      |-> Primo Search API (proxy, server-side key)
                                      |-> LLM API (structured JSON output, server-side key)
```

**Naming convention:** LLM JSON output uses snake_case (as in the schemas in the feature files); the
server validates it with Zod and maps it to camelCase for the API and Mongo.

Orchestration is the novel engineering: it turns a plain search box into the LLM behaviours
in the feature files. LLM: default to a cheap, fast model; escalate only where testing shows
the scoring quality is not good enough. Calls use structured output validated with Zod.

## Non-functional requirements

- Batch scoring, Primo caching, server-side secrets (rules 5 and 7 above).
- Blur-triggered direction generation (call 5.1) costs money: client-side unchanged-input hash
  check **and** a per-user server rate limit on `POST /api/search-directions/generate`.
  Target: feels immediate (a few seconds), fast model; the loading state never blocks typing.
- The repo is public: never commit `.env`, API keys, database URIs or participant data.
